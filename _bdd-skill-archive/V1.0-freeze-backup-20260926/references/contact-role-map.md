# Contact Strategy · 联系策略

**回答两个问题：找谁 + 什么时机找。**

**本文件只输出岗位角色，不输出具体人名。**

> **V1 冻结说明**：本文件原为纯岗位映射。V1 从已归档的 `reply-playbook.md` 迁入了两项**属判断范畴**的内容：
> ① 接触战略（场景选择逻辑，原 reply-playbook L3-8）
> ② 触发信号（定向接触时机，原 reply-playbook L196-201）
> 回复话术模板与跟进节奏 Day 0~30 属执行，未迁入（已归档）。

## 一、硬性约束（不可绕过）

| # | 约束 |
|---|---|
| 1 | **默认只推荐岗位角色**，例如「环保负责人」「技术总工」「工艺设计师」 |
| 2 | **禁止生成**具体人名、电话、邮箱、微信号、社交账号 |
| 3 | 仅当**公开来源确实查到**真人信息时，才可展示 `Name + Position + Source` |
| 4 | 公开来源限定为：企业官网、政府公示文件、招投标公告、上市公司公告、官方媒体报道 |
| 5 | 查不到 → 输出 `No verified contact found`。**不得用"可能是张工"这类表述** |
| 6 | 不得从询盘签名栏推断出联系方式以外的信息（签名栏本身就是一种来源，可标注为「客户自述」） |

> **为什么严格**：LLM 极易顺着"帮我找联系人"编出一个看起来合理的姓名，销售会真的去打。既浪费时间，也可能触及个人信息合规问题。

### Evidence 要求（遵循 `evidence-policy.md`）

| 结论 | 类型 | 要求 |
|---|---|---|
| 岗位角色（由客户类型推导） | **INFERENCE** | 必须有 `Reason`（哪条判据推出该类型）|
| `Name + Position + Source`（公开来源查到真人） | **FACT** | 必须有 `Source`（官网 / 政府公示 / 招投标公告 / 上市公告 / 官方媒体）|
| 查不到真人 | **UNKNOWN** | 输出 `No verified contact found`，**不得补全** |
| 客户类型本身为 `Unconfirmed` | **UNKNOWN** | 不推荐其他岗位，`Next Action` 为"确认客户类型" |

**禁止**：不得因"通常这类公司都有环保负责人"而输出具体姓名——行业常识不构成 Source。

## 二、客户类型 → 推荐联系岗位序列

按顺序尝试。**第一位是首选接触点。**

### 1. 终端业主（工厂）

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **环保负责人 / 安环部负责人** | 首选。技术认可的实际把关人，通常也是询盘发起方 |
| ② | **技术总工 / 生产技术负责人** | 技术方案需要上升到生产线层面时 |
| ③ | 设备科 / 采购经理 | 进入商务阶段后 |
| ④ | 总经理 / 老板 | 中小民企可跳过前几层直达；大企业不宜越级 |

**说明**：直接找老板谈技术往往无效。应先取得环保负责人的技术认可。

### 2. 环保工程公司（EPC / 集成商）

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **工艺工程师 / 技术工程师** | 首选。负责选型，决定用谁的电极 |
| ② | 项目经理 | 项目已中标、进入执行期 |
| ③ | 采购 | 进入商务阶段后 |
| ④ | 技术总监 / 总工 | 技术争议或需要厂家背书时 |

**说明**：这类客户节奏快，技术工程师是关键人。

### 3. 设计院

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **工艺设计师（水处理专业）** | 首选。决定设备选型规格 |
| ② | 专业负责人 / 主任工程师 | 需要将品牌写入设备选型清单时 |
| ③ | 项目负责人 | 整体进度协调 |

**说明**：不直接采购，但决定了后面所有供应商的规格。**最高杠杆的接触点。**

### 4. 科研院所 / 高校

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **课题负责人（老师 / 教授）** | 首选。决定买不买、买多少 |
| ② | 博士生 / 研究生（实验执行人） | 对接技术细节与规格 |
| ③ | 实验室采购 / 设备处 | 走流程、开票 |

**说明**：金额小、决策快，不要用项目销售话术。

### 5. 贸易商 / 中间商

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **负责人 / 老板** | 通常一人决策 |
| ② | — | — |

**说明**：必须索要终端信息，否则只报标准价。不投入技术支持资源。

### 6. Unconfirmed（类型未确认）

| 顺序 | 岗位 |
|---|---|
| ① | 询盘发起人（保持现有接触点，不主动升级） |

**说明**：类型未确认前不推荐联系其他岗位。第一轮回复中应先通过提问确认客户类型。

## 三、输出格式

### 情况 A：仅推荐角色（默认）

```
Recommended Contact Role: 环保负责人 / 技术总工
```

### 情况 B：公开来源查到真人

```
Recommended Contact Role: 环保负责人
  Name: {姓名}
  Position: {职位}
  Source: {URL 或来源全名}
```

### 情况 C：查不到

```
Recommended Contact Role: 环保负责人
  No verified contact found
```

**注意**：情况 B 与 C 中，**岗位角色仍然输出**。检索不到真人不影响推荐岗位——岗位是由客户类型推导的，不需要检索。

## 四、接触战略（场景选择）

**依据 `Demand Evidence` + `Commercial Risk` 的组合决定接触策略，而非单一的真伪标签。**

| Demand Evidence | Commercial Risk | 接触策略 |
|---|---|---|
| Confirmed / Strong Signal | Low / Medium | **正常推进**：索要缺失数据 + 邀请寄样小试 |
| Confirmed / Strong Signal | High | **先收紧再推进**：先确认真实性 / 走保密流程，再推进寄样 |
| Potential | Low / Medium | **先补证据**：通过提问确认项目是否存在，暂不投入技术资源 |
| Potential | High | **先补证据 + 收紧**：不释放案例与参数 |
| Weak | 任意 | **低投入**：只维持接触点，不投技术资源 |
| Unknown | 任意 | **先确认类型与需求**：保持现有接触点，不主动升级 |

### 两条关键规则

1. **两者可同时成立**（需求很实 + 风险很高）→ 此时**先按高风险收紧，再按强需求推进**，不得二选一。
2. **需求强不等于风险低。** `Demand Evidence = Strong Signal` 与 `Commercial Risk = High` 是正交维度。

## 五、触发信号（定向接触时机）

看到以下信号时定向联系客户，转化率远高于日常跟进。**这些信号同时是 BDD Relevance 与 Demand Evidence 的证据来源。**

| 触发信号 | 接触切入角度 |
|---|---|
| 客户被环保处罚 | "注意到贵司近期的情况，我们在整改类项目上有成熟经验" |
| 客户环评公示 / 技改公示 | "看到贵司 [项目] 的公示，需要废水处理段的技术支持吗" |
| 排放标准加严 / 地方新规 | "新标准对 [指标] 的要求提高了，您现有工艺可能需要评估" |
| 客户新增产线 | "新增产线后废水量和水质可能有变化，建议提前评估" |
| 客户招聘环保工程师 | 说明在有动作 |

**说明**：上表左列为**检索信号**（属背调产物），右列为**接触切入点**。本 Skill 负责识别信号；实际接触与跟进节奏属执行范畴。
