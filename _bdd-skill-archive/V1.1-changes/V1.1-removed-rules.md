## 二、R1 · 输出必含"建议小试"

### 2.1 V1.0 原文

**出处 A**：`SKILL.md` 第七节「硬性约束」第 15 条

```
| 15 | 输出必含"建议小试"（在 Next Action 或附录） | 行业标准流程 + 风险防火墙 |
```

**出处 B**：`assets/output-card-template.md:33`（主卡字段填写规则）

```
| Next Action | {一句话，含"建议小试"或具体推进动作} |
```

**出处 C**：`references/must-ask-params.md:130`（数据缺失处理）

```
| 客户要求"先给个大概价" | 不给任何数字 | 输出缺项清单 + 小试建议（**报价判断由人工处理**） |
```

### 2.2 删除原因

| # | 原因 |
|---|---|
| 1 | **越界**。寄样小试是**执行动作**，属 Boromond 工程师与销售的职责，不在情报分析 Skill 的权限内。 |
| 2 | **强制输出会制造假动作**。当 `Demand Status = Unknown` / `Path = Undetermined` 时，"建议小试"是无依据的条件反射，会让业务员误判客户已具备推进条件。 |
| 3 | **与 `Sales Conclusion` 五值冲突**。`建议先验证` 的正确 `Next Action` 是"去拿那个缺失信息"，而不是"推进小试"。 |
| 4 | **风险防火墙职责已由其他字段承担**。数据不足的兜底应由 `Missing Critical Information` + `Sales Conclusion` 表达，不需要靠"建议小试"兜底。 |

### 2.3 替代写法（V1.1）

| 场景 | V1.1 正确输出 |
|---|---|
| 通用 | `Next Action` 一句话，与决策链末端一致，**不得写"邀请寄样小试"** |
| 已确认存在具体项目 | **只写「转交技术评估流程」** |
| 结论为 `建议先验证` | `Next Action` 必须是"去拿那个缺失信息" |
| 数据缺失 | 列 `Missing Critical Information` 三级优先级（Business → Project → Technical） |

## 三、R2 · 固定输出"寄 5~10 L 水样"

### 3.1 V1.0 原文

**出处 A**：`assets/output-card-template.md:174`（填写示例 Next Action）

```
| Next Action | 索要 ①②③④ 四项并邀请寄 5~10 L 水样做免费小试 |
```

**出处 B**：`SKILL.md:357-358`（联系策略 · 接触战略表）

```
| Confirmed / Strong Signal | Low / Medium | **正常推进**：索要缺失数据 + 邀请寄样小试 |
| Confirmed / Strong Signal | High | **先收紧再推进**：先确认真实性 / 走保密流程，再推进寄样 |
```

**出处 C**：`references/contact-role-map.md:139-140`（同表，重复出现）

```
| Confirmed / Strong Signal | Low / Medium | **正常推进**：索要缺失数据 + 邀请寄样小试 |
| Confirmed / Strong Signal | High | **先收紧再推进**：先确认真实性 / 走保密流程，再推进寄样 |
```

**出处 D**：`references/must-ask-params.md:126`

```
| 客户不知道水质数据 | 不要用同类行业经验值替代 | 建议送 CMA 检测，或先寄水样做小试 |
```

### 3.2 删除原因

| # | 原因 |
|---|---|
| 1 | **越界**。"寄 5~10 L 水样"是采购/物流动作与商业条件（免费与否、批次、运费），Skill 无权承诺。 |
| 2 | **写死数值不成立**。水样规格取决于污染物类型与试验设计，5~10 L 是经验值，不应作为固定输出。 |
| 3 | **泄露内部流程**。对外输出中固定引用内部小试规格，等于把内部 SOP 暴露给客户。 |
| 4 | **可能构成效果暗示**。"邀请免费小试"隐含"我们能处理"的承诺倾向，触碰"不承诺处理效果"边界。 |

### 3.3 替代写法（V1.1）

| 场景 | V1.1 正确输出 |
|---|---|
| 客户不知水质数据 | 只列 **Technical 级缺失项**；不得给检测机构建议以外的执行动作 |
| 需求已确认 | `Next Action` = `转交技术评估流程` |
| 接触战略 | 只输出 **岗位角色 + 接触时机**，不输出推进动作细节 |

## 五、R4 · 无废水信号 → BDD Relevance 最高 `Medium`（结构性封顶）

### 5.1 V1.0 原文

**出处**：`references/bdd-relevance-rules.md:95-100`（第三节 · 判定流程 · 封顶表）

```
| 缺失项 | 封顶 |
|---|---|
| 无制造业活动证据 | `Medium` |
| 无废水信号 | `Medium` |
| 无环境证据 + 无项目信号 | `Medium` |
| 主体未核实 | `Unknown` |
```

**配套约束**：`SKILL.md:379` 硬性约束 5

```
| 5 | 无废水信号 + 无环境证据 → BDD Relevance 最高只能 `Medium` | 防止行业经验值升格 |
```

**输入定义**：`references/bdd-relevance-rules.md:23`

```
| 6 | **Wastewater Signals** 废水信号 | 询盘文字 → `wastewater-signal-map.md` | 必须 |
```

> 关键问题：**废水信号的唯一来源被限定为"询盘文字"**。

### 5.2 删除原因

| # | 原因 |
|---|---|
| 1 | **规则死锁（5 次实跑连续复现）**。Hikal / Aarti / Umicore / EnviroChemie 四家均有公开废水证据（排污许可、环评、ETP 公示），但因"无询盘文字"全部被封顶 `Medium`。 |
| 2 | **口径倒置**。背调的**目的**是无需询盘也能判断机会。"必须有询盘才能给 High"使 Skill 在主动开发场景下失效。 |
| 3 | **行业经验值风险已有更好的防线**。V1.1 改为要求 `High` 必须有 **≥ 2 项主体级证据编号**，比一刀切封顶更精准。 |
| 4 | **封顶掩盖真实差异**。四家实际证据强度差别很大（Umicore 有多个厂区级环评 + 电池回收业务），却输出同一档位，失去排序价值。 |

### 5.3 替代写法（V1.1）

**核心结构性变更：废水证据拆成两类，分别定级。**

| 类型 | 全称 | 来源 | 是否受"有无询盘"限制 |
|---|---|---|---|
| `PWE` | Public Wastewater Evidence · 公开废水证据 | 排污许可 / 环评 / 处罚 / ESG / 招投标 | **否** |
| `CSD` | Customer-stated Demand · 客户侧需求陈述 | 询盘文字 / 聊天记录 / 名片附言 | 是（本身即询盘） |

**新规则**：
- `PWE` 单独成立即可支撑 `BDD Relevance = High`（**不再封顶**）
- `Demand Status` 在 `End-user Path` 下取 PWE 与 CSD 两者**较高者**
- `High` 硬门槛改为：`Reason` 必须列出 **≥ 2 项主体级证据编号**
